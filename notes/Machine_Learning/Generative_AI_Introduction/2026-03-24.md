## Flash Attention

- Does not change the result from Attention (nothing except speed changes)
- Model-agnostic for any model using attention (plug-and-play)
- Solve memory bandwidth bottleneck from moving data in-and-out between SRAM and HBM

### How GPU computes?

- Analogy characters
  - Worker: Execution unit
  - Work Desk: SRAM (small space)
  - Storage: HBM (large space)
- Pipeline for computation
  1. Worker moves data from storage to work desk (slow)
  2. Worker works in the work desk (fast)
  3. Worker moves result back to storage (slow)

### How Flash Attention works?

- Description:
  - When calculating QKV result $(\frac{QK^T}{\sqrt{d_k}}V)$, data is moved between work desk and storage lots of times
  - Therefore the goal is to reduce the data movement between work desk and storage
  - Calculate QKV result with only one time data movement (end-to-end)
    - For the first work desk, use whatever inputs within it to calculate QKV result
    - For the next work desk,
      - Compare the factors stored and used in previous calculation
      - If the calculation is wrong, correct previous results with new factors
      - Store the factors for the next work desk
    - So on and so forth until reaching the final work desk
- Pros:
  - Speed up generation speed especially for long context
  - Reduce memory footprint during training since no intermediate attention matrix is stored
- Cons
  - Require extra computation (which is usually negligible compared to data movement)

## KV Cache

- KV Cache
  - Description:
    - Key (K) and Value (V) calculated from previous queries can be stored and re-used
  - Pros:
    - Attention remains intact
  - Cons:
    - Require lots of memory especially when using multi-head attention (x number of head)
- Multi-query Attention
  - Description:
    - All queries share the same one set K, V
  - Pros:
    - Decrease memory usage
  - Cons:
    - Degrade model accuracy
    - Attention changes
- Grouped-query Attention (Llama, Gemma)
  - Description:
    - Groups of query heads share a single K, V
    - e.g., query 1 and query 2 share KV 1, query 3 and query 4 share KV 2, so and so on
  - Pros:
    - Balance between KV cache and Multi-query attention in both memory usage and model accuracy
  - Cons:
    - Model must be trained to use new attention mechanism
    - Attention changes
- Multi-head Latent Attention (MLA) (DeepSeek)
  - Description:
    - Compress KV Cache and calculate with compressed KV Cache in compression space directly
  - Cons:
    - Model must be trained to use new attention mechanism
    - Attention changes
- Sliding Window Attention
  - Description:
    - Change the range of attention for KV Cache
      - Mistral 7B: Only keep fixed size of KV Cache for all attention layers
      - GPS-OSS: Some attention layers keep fixed size KV Cache, some still keep full size KV Cache
  - Pros:
    - KV Cache size is predictable
  - Cons:
    - Attention changes
- Streaming LLM
  - Description:
    - Sliding window attention with prepended KV from the FIRST few tokens
  - Pros:
    - Improve model accuracy while keeping advantages of sliding window method
    - Why it works?
      - For the first token, there is no attention to be calculated
      - Therefore if there is nothing to attend in new query, model falls back to attend the first (few) tokens
      - So if there are no first few tokens provided when there is nothing to attend, there are no fallback for models
- Pruning KV Cache
  - Description:
    - Drop non-used K, V in KV Cache
  - Pros:
    - Reduce memory usage significantly
  - Cons:
    - May degrade model accuracy for complex task
    - Attention changes

### Speculative Decoding

- Pipeline
  - Use draft model to guess the next, and the next next token that will be generated
  - Generate following tokens w/ LLM *AT THE SAME TIME*
    1. Origin query token
    2. Origin query token + predicted next token
    3. Origin query token + predicted next token + predicted next next token
  - Compare the output token from origin query token by LLM to the predicted next token
    - If the predicted next token is not correct
      - Just use the token generated from original query token as output token
    - If the predicted next token is correct,
      - Take the predicted next token as output token
      - Compare the output token generated from origin query token + correctly predicted next token
        - If the predicted next next token is wrong,
          - DO NOT take the output next next token generated using the wrongly predicted token
- Key Message
  - Since we process 3x query at the same time, we need 3x of computation
  - The time difference comes in the draft model prediction,
    - If the prediction is fast enough to ignore,
      - Then even in the worst case, the time does not change much
      - But for the best case, the time only takes 1/3 compared to original autoregressive process
- Draft model candidates (for fast speed)
  - Non-autoregressive Model
  - Compressed Model (smaller LLM)
  - Search Engine

### Prompt-Caching

- For chats or agents sharing system prompt across sessions,
  - System prompt KV can be cached to reduce computation
- Therefore, for computation efficiency, static input like system prompt should be put in the front of context
